## 2. Problem

A scheduling service must never book a provider for two overlapping active appointments. The slice to build:
- **Book** an appointment for a provider over a time interval.
- **Cancel** an appointment, which frees its time slot.

## 5. Booking Invariant

> For any provider, no two **ACTIVE** appointments overlap.

Intervals are **half-open**: `[start, end)`. Two intervals `a` and `b` overlap exactly when:

```
a.start < b.end  &&  b.start < a.end
```

**The same rule, stated as "no overlap".** Two intervals do *not* overlap when one ends at or before the moment the other starts:

```
a.end <= b.start  ||  b.end <= a.start
```

This is the exact negation of the overlap condition (De Morgan: `!(x && y) == !x || !y`, and `!(a.start < b.end)` is `b.end <= a.start`). The code uses the overlap form, but either one works. Visually:

```
no overlap:   a: [=====)              a ends at or before b starts
                       b: [=====)
no overlap:   b: [=====)              b ends at or before a starts
                       a: [=====)
overlap:      a: [=======)            neither of the above is true
                   b: [=======)
```

- **Adjacency is allowed automatically.** If `a.end == b.start`, then `b.start < a.end` is false, so there is no overlap.
- **Only ACTIVE appointments count.** CANCELLED appointments are ignored by the check.
- **The invariant lives in `BookingService` only.** No other class enforces it.

## 6. Assumptions

| Area | Assumption |
|---|---|
| Time zone | All timestamps are UTC, in ISO-8601 with a `Z` suffix, e.g. `2026-11-20T10:00:00Z`. Offsets like `+05:30` are rejected. |
| Input format | A booking is given as start + end. Duration = end - start, and it must be > 0. |
| Past bookings | Allowed. The spec has no "now" rule. |
| Limits | No maximum duration, no business hours, no minimum slot size. |
| IDs | Appointment IDs are UUIDs generated by the service. Provider IDs are any non-blank string. |
| Persistence | In memory only. Data is lost when the program exits. |
| Threading | Single-threaded through P4. P5 adds one lock in `BookingService` (see Section 12). |
| History | Cancelled appointments are kept with status CANCELLED, not deleted. |

## 9. Data Design: InMemoryAppointmentStore

```java
Map<String, Appointment>  byId;        // the only place appointments are kept
Map<String, List<String>> byProvider;  // providerId -> appointment ids
```

**Why `byProvider` holds ids, not appointments.** Records are immutable, so cancelling **replaces** the record in `byId`. If `byProvider` held `Appointment` objects, it would keep a stale ACTIVE copy. With ids, `byId` is the only place that needs updating.

**Methods**

| Method | Behavior |
|---|---|
| `save(Appointment a)` | Puts or replaces `a` in `byId`. Adds `a.id()` to `byProvider` only on the first save of that id (when `byId.put` returns no previous record). Replace-on-save exists for cancel. |
| `findById(String id)` | Returns `Optional<Appointment>`. |
| `findByProvider(String providerId)` | Returns all appointments for that provider, ACTIVE and CANCELLED, looked up through the ids in `byId`. Returns an empty list if the provider is unknown. |

**Decided (P3): cancelling keeps the id in `byProvider`.** The overlap check filters by `status == ACTIVE`.
- Reason: "is it active" has a single source of truth, which is the `status` field. Cancel stays a single write, and `list` can still show cancelled appointments.
- Rejected alternative: removing the id on cancel, with the map renamed to `activeByProvider`. That means two writes per cancel and two places that encode "active".

**Assumption:** a re-save never changes `providerId`. `cancel()` keeps every field except `status`, and nothing else re-saves.

**Not thread-safe on its own.** The store uses plain `HashMap` / `ArrayList`. It is safe because it is reached only through `BookingService` methods that hold the service's lock (Section 12).

## 10. Service API: BookingService

```java
public BookingService(InMemoryAppointmentStore store)

public BookingResult     book(String providerId, String start, String end)
public CancelResult      cancel(String appointmentId)
public List<Appointment> listForProvider(String providerId)   // read-only, for the REPL and debugging
```

`book` and `cancel` are the feature. `listForProvider` is a convenience and is outside the required scope.

**Inputs are raw strings on purpose.** The service does the parsing, so invalid timestamps can be tested at the service level (AC5).

**No exceptions for business outcomes.** A conflict or bad input is an expected result, returned as a value.

### 10.1 `book` flow

```
1. Validate (no store access yet)
   a. providerId is null or blank         → Rejected(INVALID_INPUT, "providerId is required")
   b. start or end is null or blank        → Rejected(INVALID_INPUT, "start and end are required")
   c. start or end has no 'Z' suffix
      or fails Instant.parse                → Rejected(INVALID_INPUT, "timestamps must be ISO-8601 UTC, e.g. 2026-11-20T10:00:00Z")
   d. end is not after start                → Rejected(INVALID_INPUT, "end must be after start")
2. Overlap check
   ACTIVE appointments of providerId where existing.start < end && start < existing.end
   any match                                → Rejected(CONFLICT, "overlaps appointment <id>")
3. Create Appointment(UUID, providerId, start, end, ACTIVE)
4. store.save(appointment)
5. return Booked(appointment)
```

Steps 2 to 4 stay together in this one method, so the P5 lock can wrap them (Section 12).

**Verified in P2:** since JDK 12, `Instant.parse` also accepts offsets. On JDK 21, `Instant.parse("2026-11-20T16:30:00+05:30")` returns `11:00:00Z`. The explicit `Z` check in step 1c is what enforces strict UTC, and T7 has an offset case that fails if the check is removed.

### 10.2 `cancel` flow

```
1. appointmentId is null or blank  → INVALID_INPUT
2. not found in store              → NOT_FOUND
3. status is CANCELLED             → ALREADY_CANCELLED
4. store.save(appointment.cancel())
5. return CANCELLED
```

## 11. CLI (Main)

An interactive REPL, so the in-memory state lasts for the whole session.

```
> book dr-smith 2026-11-20T10:00:00Z 2026-11-20T11:00:00Z
BOOKED  id=<full uuid>  dr-smith  2026-11-20T10:00:00Z to 2026-11-20T11:00:00Z
> book dr-smith 2026-11-20T10:30:00Z 2026-11-20T11:30:00Z
REJECTED  CONFLICT: overlaps appointment <full uuid>
> cancel <full uuid>
CANCELLED
> list dr-smith
<full uuid>  2026-11-20T10:00:00Z to 2026-11-20T11:00:00Z  CANCELLED
> help
> exit
bye
```

As built (P4), the output prints full ids, since `cancel` needs them, and full ISO timestamps, so the date is visible. See `evidence/cli-demo-scripted.txt` (scripted) and `evidence/cli-demo-manual.txt` (manual) for real sessions.

| Command | Action |
|---|---|
| `book <providerId> <start> <end>` | Calls `book` and prints the result. |
| `cancel <appointmentId>` | Calls `cancel` and prints the result. |
| `list <providerId>` | Prints all of that provider's appointments. |
| `help` | Shows the commands. |
| `exit` | Quits. |

A line with the wrong number of arguments prints a usage message, and an unknown command prints a hint. The CLI does no validation of its own; it passes the strings to the service.

**Note (found in the manual demo):** the CLI splits on whitespace, so a blank argument can't reach the service. `cancel` or `cancel   ` is a usage error. `CancelResult.INVALID_INPUT` and the blank-field `book` rejections are therefore reachable only through the service API, where the service tests cover them. This is intended: AC5 applies to any caller.

`list` shows appointments in booking order, not sorted by start time.

## 12. Concurrency (P5)

**Risks**
1. **A check-then-act race in `book`.** Two threads both run the overlap check, both see the slot free, and both save. That leaves two overlapping ACTIVE appointments.
   ```
   Thread A: overlap check → free ─┐
   Thread B: overlap check → free  │  both checks happen before either save
   Thread A: save 10:00–11:00      │
   Thread B: save 10:30–11:30 ─────┘  → invariant broken
   ```
2. **The same race in `cancel`.** Two threads cancel one id, both see ACTIVE, and both return `CANCELLED`. One should get `ALREADY_CANCELLED`.
3. **The store is not thread-safe.** Concurrent writes to `HashMap` / `ArrayList` can lose an id, and reading a list while another thread appends to it can throw `ConcurrentModificationException`. Without synchronization, one thread may not see another's writes. This applies even to bookings that don't conflict, or are for different providers.

**Decisions (agreed before implementation)**

| # | Decision | Reason |
|---|---|---|
| 1 | **One `private final ReentrantLock`** in `BookingService`, always used as `lock(); try { … } finally { unlock(); }` | Makes the locked section explicit, and always releases the lock, even on an early `return` or an exception. Preferred over `synchronized`. A `synchronized` method was ruled out because it would put validation inside the lock. |
| 2 | **`book`:** validation (step 1) outside the lock. Steps 2 to 4 (overlap check, create, save) inside. | Validation reads only the method's own arguments and immutable `Instant`s, so it is safe to run in parallel, and the locked section stays short. |
| 3 | **`cancel`:** the blank-id check outside. `findById`, the status checks and the save inside. | Closes risk 2. |
| 4 | **`listForProvider` is locked too** (beyond the original plan). | It reads a provider's `ArrayList`, which a concurrent booking may be appending to. `findByProvider` returns a snapshot, so the caller can use it after unlock. Every store access then goes through the lock. |
| 5 | **The store stays as it is**: plain collections, no locking of its own. | The service lock guards every access (risk 3), and also guarantees each thread sees the previous thread's writes. It keeps the store dumb (Section 7). |
| 6 | **No per-provider locks.** | See the trade-off below. Listed in Section 17. |

**Trade-off: one lock vs per-provider locks**
- With one lock, bookings for *different* providers also wait for each other, though they can never conflict. That costs throughput, not correctness, and is negligible at this scale.
- Per-provider locks, e.g. a `ConcurrentHashMap<String, ReentrantLock>`, would remove that waiting, but only with more changes:
  - The store's maps and lists would have to be thread-safe, because providers share one `HashMap`.
  - `cancel` would have to look up the appointment first to learn its provider, take that provider's lock, then re-read the appointment in case it changed.
- That means more moving parts and more ways to get it wrong, for a gain nobody needs here.

**Test (`BookingServiceConcurrencyTest`)**
- An `ExecutorService` of 50 threads. Each round uses a fresh store and service.
- Thread *i* books `dr-smith` for `10:00 + i min` to `11:00 + i min`, so every pair of intervals overlaps.
- Two `CountDownLatch`es line the threads up: each signals "ready" and waits for "go", and the main thread releases them all at once.
- Each round must end with exactly 1 `Booked`, 49 `Rejected(CONFLICT)` and 1 appointment in the store. An exception from any thread fails the test.
- Repeated for many rounds (about 200), because a race may not show up in one run.
- Gate (Section 15): the test passes with the lock. It must also fail when the lock is removed, checked in a throwaway copy outside the repo.
- **Added during the build:** a second test, `concurrentCancelsOfOneAppointmentLetExactlyOneSucceed`. 50 threads cancel one appointment; exactly one gets `CANCELLED`, the rest `ALREADY_CANCELLED`. It tests risk 2. It wasn't in the agreed list; it was flagged afterwards, and I kept it.
- **Result:** both tests pass with the lock. With the lock removed, both fail, checked by Claude Code (scratch copy) and by me (real code): bookings `expected <1> but was <50>`, cancels `but was <2>`/`<3>`. My run is saved in `evidence/concurrency-tests-fail-without-lock.txt`.

## 13. Test Plan

**Core tests (must have, one per AC6 category)**

| # | Test | AC |
|---|---|---|
| T1 | A valid booking returns `Booked`, and the appointment is stored as ACTIVE. | AC1 |
| T2 | An overlapping booking for the same provider returns `Rejected(CONFLICT)`. | AC2 |
| T3 | A booking that starts exactly when another ends returns `Booked`. | AC3 |
| T4 | The same interval for two different providers: both return `Booked`. | AC2 |
| T5 | Cancel, then rebook the same slot: returns `Booked`. | AC4 |
| T6 | Cancelling a missing ID returns `NOT_FOUND`. Cancelling twice returns `ALREADY_CANCELLED`. | AC4 |
| T7 | Invalid input returns `Rejected(INVALID_INPUT)` with the exact message, and the store is unchanged. Built as one parameterized test with 9 cases: null/blank provider, null start, blank end, unparseable timestamp, date with no time, `+05:30` offset, zero duration, negative duration. | AC5 |
| (extra) | Cancelling with a null, empty or blank id returns `INVALID_INPUT`, and the store is unchanged. | AC5 |

**Done:** T1 to T7 and the blank-id cancel test (P2/P3), and the 5 store tests (P1). The offset, zero-duration and negative-duration stretch cases were pulled forward into T7 in P2, because the P2 gate required checking the `Z` check.

**Concurrency test (P5):** see Section 12. It is required by the P5 gate, so it is no longer a stretch item.

**Stretch tests not built (decided in P6):** partial overlap at the start, full containment, identical interval, and reverse adjacency. I decided the core tests plus the mutation checks were enough.

**Mutation checks done so far** (throwaway copies, not the repo), each caught by exactly one test:
- Removing the `Z` check → the T7 offset case fails.
- Making the overlap check inclusive (`<=`) → T3 fails.
- Ignoring status in the overlap check → T5 fails.
- Removing the ALREADY_CANCELLED check → T6 (cancel twice) fails.

**Rules**
- A fresh store and service for each test (`@BeforeEach`).
- Fixed UTC timestamps, never `Instant.now()`.

## 17. Known Limitations (to finish after the build)

- In-memory only: no durability, and nothing is shared across processes.
- The overlap check scans every appointment for the provider, which is O(n) per booking. Fine at this scale. An interval tree or sorted structure would scale better.
- A single lock (P5) serializes all bookings, cancels and lists, including those for different providers that can never conflict. This costs throughput, not correctness. Per-provider locks would fix it, but would need a thread-safe store and a look-up-then-re-check step in `cancel` (Section 12).
- Blank arguments can't reach the service through the CLI, because whitespace splitting turns them into usage errors. The service still rejects them for any other caller (Section 11).
- No limits on duration, booking in the past, or how far ahead a booking can be.
- Cancelled appointments are never cleaned up, so memory grows over time.
