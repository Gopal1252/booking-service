## 1. Service boundary

No starter project was supplied, so this follows the assessment's fallback: **a small service with a CLI and an in-memory store**. Only the booking-conflict and cancellation slice is built.

```
Main (CLI REPL)              parses a line, calls the service, prints the result; no validation of its own
      │
BookingService               the boundary: validation, the booking invariant, locking
      │
InMemoryAppointmentStore     storage and lookups only; no rules
```

- `BookingService` is the only place rules live. Everything above it (CLI, tests) passes raw input in. Everything below it (the store) only stores.
- Dependencies point downward only. Tests call `BookingService` directly, not through the CLI.
- Out of scope, as required: frontend, HTTP, auth, notifications, recurring availability, calendar integration, database, deployment.

## 2. Data and API design

**Model**
- `Appointment` is an immutable record: `id` (UUID string, generated by the service), `providerId`, `start`, `end` (`Instant`, UTC), `status`.
- `Status` is `ACTIVE` or `CANCELLED`. `appointment.cancel()` returns a copy with status `CANCELLED`; records are never changed in place.

**API** (`BookingService`)

```java
BookingResult     book(String providerId, String start, String end)   // timestamps like 2026-11-20T10:00:00Z
CancelResult      cancel(String appointmentId)
List<Appointment> listForProvider(String providerId)                 // read-only helper for the CLI
```

| Result | Values |
|---|---|
| `BookingResult` (sealed) | `Booked(appointment)` or `Rejected(reason, message)`, where reason is `INVALID_INPUT` or `CONFLICT` |
| `CancelResult` (enum) | `CANCELLED`, `NOT_FOUND`, `ALREADY_CANCELLED`, `INVALID_INPUT` |

- **Outcomes are values, not exceptions.** A conflict or bad input is an expected result.
- **Inputs are raw strings.** The service parses and validates, so invalid input can be tested at the boundary.
- **`book`:**
  1. Validate: provider present; timestamps present, ISO-8601, ending in `Z`; `end > start`.
  2. Check for overlap with the provider's ACTIVE appointments.
  3. Create the appointment and save it.

  Validation runs **before any store access**, so a rejected call never changes stored bookings.
- **`cancel`:** blank id → `INVALID_INPUT`; unknown id → `NOT_FOUND`; already cancelled → `ALREADY_CANCELLED`; otherwise it saves the cancelled copy → `CANCELLED`.

## 3. Booking invariant

> **For any provider, no two ACTIVE appointments overlap.**

Intervals are half-open, `[start, end)`. Two intervals overlap exactly when:

```
a.start < b.end  &&  b.start < a.end        (equivalently, they don't overlap when a.end <= b.start || b.end <= a.start)
```

- **Adjacent appointments are allowed.** If one ends at 11:00 and the next starts at 11:00, they don't overlap.
- **Only ACTIVE appointments count.** A cancelled appointment no longer blocks its time.
- **Different providers never conflict.** The check only looks at the same provider's appointments.
- Enforced in one place only: `BookingService.book`.

## 4. Persistence approach

In memory, inside `InMemoryAppointmentStore`:

```java
Map<String, Appointment>  byId;        // the only place appointments are kept
Map<String, List<String>> byProvider;  // providerId -> appointment ids
```

- `byProvider` holds **ids, not records**. Cancel replaces the record in `byId` under the same id, so the index never holds a stale copy.
- Cancelled appointments are **kept** with status `CANCELLED`, not deleted. "Is it active?" has one source of truth, the `status` field. The overlap check filters on it.
- Data lasts for one CLI session and is lost on exit. The CLI is an interactive REPL for this reason: state survives across commands.

## 5. Concurrency approach

**Risk:** check-then-act. Two threads both find a slot free and both save, which gives two overlapping appointments. The store's plain `HashMap`/`ArrayList` are also not safe for concurrent use.

**Approach:** one `ReentrantLock` in `BookingService`, always used as `lock(); try { … } finally { unlock(); }`.

| Method | Outside the lock | Inside the lock |
|---|---|---|
| `book` | validation (reads only its own arguments) | overlap check, create, save |
| `cancel` | blank-id check | find, status checks, save |
| `listForProvider` | | read (returns a snapshot copy) |

Every store access goes through the lock, so the store itself needs no thread safety.

**Test:** `BookingServiceConcurrencyTest`, 50 threads × 200 rounds, released together by latches:
- Overlapping bookings for one provider: exactly 1 succeeds.
- Concurrent cancels of one appointment: exactly 1 returns `CANCELLED`.

With the lock removed, both tests fail (all 50 bookings succeed), as shown in `evidence/concurrency-tests-fail-without-lock.txt`.

## 6. Key assumptions and trade-offs

**Assumptions**

| Area | Assumption |
|---|---|
| Time zone | UTC only. Timestamps must be ISO-8601 with a `Z` suffix. Offsets like `+05:30` are rejected. Since JDK 12, `Instant.parse` accepts offsets, so `Z` is checked explicitly. |
| Input | A booking is given as start + end, and duration must be > 0. Past bookings are allowed. No maximum duration and no business hours. |
| Identifiers | Appointment ids are service-generated UUIDs. Provider ids are any non-blank string supplied by the caller. They are not trimmed, and no provider registry exists. |
| History | Cancelled appointments are kept, not deleted. |

**Trade-offs**
- **One global lock instead of per-provider locks.** Simple and correct, but bookings for different providers also wait for each other. Per-provider locks would need a thread-safe store, plus a look-up-then-re-check step in `cancel`. That is more complexity than this scale needs.
- **Keep cancelled ids in the index instead of removing them.** One write per cancel, with a single source of truth for "active", at the cost of scanning cancelled entries.
- **Linear overlap scan.** O(n) per provider per booking. Fine at this scale; an interval tree or sorted structure would scale better.
- **Raw-string API.** Keeps all validation in the service and testable, at the cost of parsing on every call.
