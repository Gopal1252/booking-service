## 2. Problem

A scheduling service must never book a provider for two overlapping active appointments. The slice to build:
- **Book** an appointment for a provider over a time interval.
- **Cancel** an appointment, which frees its time slot.

## 5. Booking Invariant

> For any provider, no two **ACTIVE** appointments overlap.

Intervals are **half-open**: `[start, end)`. Two intervals `a` and `b` overlap exactly when:

```
a.start < b.end  &&  b.start < a.end
```

**The same rule, stated as "no overlap".** Two intervals do *not* overlap when one ends at or before the moment the other starts:

```
a.end <= b.start  ||  b.end <= a.start
```

This is the exact negation of the overlap condition (De Morgan: `!(x && y) == !x || !y`, and `!(a.start < b.end)` is `b.end <= a.start`). The code uses the overlap form, but either one works. Visually:

```
no overlap:   a: [=====)              a ends at or before b starts
                       b: [=====)
no overlap:   b: [=====)              b ends at or before a starts
                       a: [=====)
overlap:      a: [=======)            neither of the above is true
                   b: [=======)
```

- **Adjacency is allowed automatically.** If `a.end == b.start`, then `b.start < a.end` is false, so there is no overlap.
- **Only ACTIVE appointments count.** CANCELLED appointments are ignored by the check.
- **The invariant lives in `BookingService` only.** No other class enforces it.

## 6. Assumptions

| Area | Assumption |
|---|---|
| Time zone | All timestamps are UTC, in ISO-8601 with a `Z` suffix, e.g. `2026-11-20T10:00:00Z`. Offsets like `+05:30` are rejected. |
| Input format | A booking is given as start + end. Duration = end - start, and it must be > 0. |
| Past bookings | Allowed. The spec has no "now" rule. |
| Limits | No maximum duration, no business hours, no minimum slot size. |
| IDs | Appointment IDs are UUIDs generated by the service. Provider IDs are any non-blank string. |
| Persistence | In memory only. Data is lost when the program exits. |
| Threading | Phase 1 is single-threaded. Phase 2 adds locking (see Section 12). |
| History | Cancelled appointments are kept with status CANCELLED, not deleted. |

## 9. Data Design: InMemoryAppointmentStore

```java
Map<String, Appointment>  byId;        // the only place appointments are kept
Map<String, List<String>> byProvider;  // providerId -> appointment ids
```

**Why `byProvider` holds ids, not appointments.** Records are immutable, so cancelling **replaces** the record in `byId`. If `byProvider` held `Appointment` objects, it would keep a stale ACTIVE copy. With ids, `byId` is the only place that needs updating.

**Methods**

| Method | Behavior |
|---|---|
| `save(Appointment a)` | Puts or replaces `a` in `byId`. Adds `a.id()` to `byProvider` if it isn't already there. |
| `findById(String id)` | Returns `Optional<Appointment>`. |
| `findByProvider(String providerId)` | Returns all appointments for that provider, ACTIVE and CANCELLED, looked up through the ids in `byId`. Returns an empty list if the provider is unknown. |

**Open decision (settle during the build):** should cancelling also remove the id from `byProvider`?
- Current choice: **keep it, and filter by `status == ACTIVE` in the overlap check.**
- Reason: "is it active" has a single source of truth, which is the `status` field.
- If the id does get removed instead, rename the map to `activeByProvider`.

## 10. Service API: BookingService

```java
public BookingService(InMemoryAppointmentStore store)

public BookingResult     book(String providerId, String start, String end)
public CancelResult      cancel(String appointmentId)
public List<Appointment> listForProvider(String providerId)   // read-only, for the REPL and debugging
```

`book` and `cancel` are the feature. `listForProvider` is a convenience and is outside the required scope.

**Inputs are raw strings on purpose.** The service does the parsing, so invalid timestamps can be tested at the service level (AC5).

**No exceptions for business outcomes.** A conflict or bad input is an expected result, returned as a value.

### 10.1 `book` flow

```
1. Validate (no store access yet)
   a. providerId is null or blank         → Rejected(INVALID_INPUT, "providerId is required")
   b. start or end is null or blank        → Rejected(INVALID_INPUT, "start and end are required")
   c. start or end has no 'Z' suffix
      or fails Instant.parse                → Rejected(INVALID_INPUT, "timestamps must be ISO-8601 UTC, e.g. 2026-11-20T10:00:00Z")
   d. end is not after start                → Rejected(INVALID_INPUT, "end must be after start")
2. Overlap check
   ACTIVE appointments of providerId where existing.start < end && start < existing.end
   any match                                → Rejected(CONFLICT, "overlaps appointment <id>")
3. Create Appointment(UUID, providerId, start, end, ACTIVE)
4. store.save(appointment)
5. return Booked(appointment)
```

Steps 2 to 4 stay together in this one method, so a lock can wrap them in Phase 2.

**Note to verify during the build:** since JDK 12, `Instant.parse` also accepts offsets like `+05:30`. The explicit `Z` check in step 1c is what enforces strict UTC. A test should confirm this.

### 10.2 `cancel` flow

```
1. appointmentId is null or blank  → INVALID_INPUT
2. not found in store              → NOT_FOUND
3. status is CANCELLED             → ALREADY_CANCELLED
4. store.save(appointment.cancel())
5. return CANCELLED
```

## 11. CLI (Main)

An interactive REPL, so the in-memory state lasts for the whole session.

```
> book dr-smith 2026-11-20T10:00:00Z 2026-11-20T11:00:00Z
BOOKED  id=3f2a...  dr-smith  10:00Z to 11:00Z
> book dr-smith 2026-11-20T10:30:00Z 2026-11-20T11:30:00Z
REJECTED  CONFLICT: overlaps appointment 3f2a...
> cancel 3f2a...
CANCELLED
> list dr-smith
3f2a...  10:00Z to 11:00Z  CANCELLED
> help
> exit
```

| Command | Action |
|---|---|
| `book <providerId> <start> <end>` | Calls `book` and prints the result. |
| `cancel <appointmentId>` | Calls `cancel` and prints the result. |
| `list <providerId>` | Prints all of that provider's appointments. |
| `help` | Shows the commands. |
| `exit` | Quits. |

A line with the wrong number of arguments prints a usage message. The CLI does no validation of its own; it passes the strings to the service.

## 12. Concurrency (Phase 2)

**Risk:** a check-then-act race. Two threads both see the slot free, and both save.

**Plan:**
- One `ReentrantLock` (or `synchronized`) in `BookingService`.
- It wraps steps 2 to 4 of `book` and the whole of `cancel`.
- Validation stays outside the lock.

**Possible upgrade:** per-provider locks, so different providers can book in parallel. Not needed at this scale.

**Test:** N threads book overlapping slots for one provider at the same time. Exactly one must succeed. The test uses an `ExecutorService` and a `CountDownLatch`, so all threads start together.

## 13. Test Plan

**Core tests (must have, one per AC6 category)**

| # | Test | AC |
|---|---|---|
| T1 | A valid booking returns `Booked`, and the appointment is stored as ACTIVE. | AC1 |
| T2 | An overlapping booking for the same provider returns `Rejected(CONFLICT)`. | AC2 |
| T3 | A booking that starts exactly when another ends returns `Booked`. | AC3 |
| T4 | The same interval for two different providers: both return `Booked`. | AC2 |
| T5 | Cancel, then rebook the same slot: returns `Booked`. | AC4 |
| T6 | Cancelling a missing ID returns `NOT_FOUND`. Cancelling twice returns `ALREADY_CANCELLED`. | AC4 |
| T7 | Invalid input (bad timestamp, `end <= start`, blank provider) returns `Rejected(INVALID_INPUT)`, and the store is unchanged. | AC5 |

**Stretch tests (if time allows)**
- Partial overlap at the start and at the end, full containment, identical interval
- Adjacency in the other direction (the new booking ends exactly when the existing one starts)
- An offset timestamp (`+05:30`) is rejected
- Zero duration and negative duration as separate cases
- The concurrency test (Phase 2)

**Rules**
- A fresh store and service for each test (`@BeforeEach`).
- Fixed UTC timestamps, never `Instant.now()`.

## 17. Known Limitations (to finish after the build)

- In-memory only: no durability, and nothing is shared across processes.
- The overlap check scans every appointment for the provider, which is O(n) per booking. Fine at this scale. An interval tree or sorted structure would scale better.
- A single lock in Phase 2 serializes all bookings, including those for different providers.
- No limits on duration, booking in the past, or how far ahead a booking can be.
- Cancelled appointments are never cleaned up, so memory grows over time.
